# 知屿 Knowledge Studio：项目面试与演示指南

> 核对日期：2026-11-02。依据当前代码、配置示例及仓库验收记录整理。先读第 1、5、7 节，可完成一次项目介绍与演示。

## 1. 项目定位与一分钟介绍

**一句话：一个面向个人资料、支持混合检索和原文核对的 RAG 知识工作台。**

解决三个问题：资料难查、跨文档关系难串联、模型答案难核实。

可以这样讲：

> 这个项目把上传的文档转换为可检索的知识。后端用 FastAPI，SQLite 保存业务记录，Milvus 检索语义相近的片段，Neo4j 补充实体之间的关系。提问时，系统先结合近期对话改写问题，再并行查询向量和图谱，融合证据后让模型生成带引用的回答。用户可以点击引用查看完整原文，也可以通过局部图谱核对跨文档关系。工程上加入了后台建库、失败补偿、重启恢复，以及完整回答落库和耗时统计。

**个人职责按实际参与范围介绍。** 项目保留了上游组件署名和 Apache 2.0 许可，不能将复用组件描述为个人从零实现。见 [NOTICE](../NOTICE)。

## 2. 技术栈：是什么、在这里做什么

版本依据 [运行依赖](../requirements.txt)、[配置示例](../.env.example)；模型名称是配置值，可替换。

| 技术 | 定义 | 项目用途与选用思路 |
| --- | --- | --- |
| Python + FastAPI 0.115.5 | Python 语言及基于类型声明的 Web API 框架 | 提供文档、问答、会话和统计接口，便于连接模型与数据处理库 |
| Uvicorn 0.32.0 | 运行 ASGI 应用的服务器 | 承载 FastAPI；当前后台队列要求单进程运行 |
| Pydantic 2.9.2 | 基于类型声明的数据校验库 | 校验问题长度、会话 ID 等请求字段 |
| LangChain 相关组件 | 连接模型、文档和检索服务的组件库 | 使用 Document、Milvus 和 ChatOpenAI 等适配器；核心业务流程由项目函数串联 |
| Sentence Transformers + Transformers + PyTorch | 文本模型封装、模型工具库和张量计算框架 | 本地加载嵌入模型，按可用硬件使用 CPU 或 CUDA |
| Jina Embeddings v3 | 将文本映射为语义向量的嵌入模型 | 配置示例使用该模型；分别以 query/passage 任务编码问题与文档并归一化 |
| ChatOpenAI + DeepSeek 模型接口 | OpenAI 兼容接口适配器与外部生成模型服务 | 执行问题改写、关系抽取和回答生成；模型由配置指定，示例为 deepseek-v4-flash |
| Jinja2 + 原生 JavaScript/CSS | 服务端模板与浏览器交互技术 | 构建工作台、知识库、问答和数据洞察页面 |
| SSE + fetch 流读取 | 服务器向客户端持续发送事件的 HTTP 流式方式 | 按顺序推送状态、来源、图谱、文字增量和完成信息 |
| Marked + DOMPurify | Markdown 解析库与 HTML 清洗库 | 支持表格、列表、代码等显示，并过滤危险 HTML |
| PyPDFLoader/pypdf + ZIP/XML 解析 | PDF 文本解析及 DOCX 内容提取方式 | 读取 PDF、DOCX；TXT/MD 支持 UTF-8 与 GB18030 |
| PDF.js + Vis Network | 浏览器 PDF 阅读组件与网络关系可视化库 | 展示 PDF 完整原件、定位高亮，以及可点击来源的局部图谱 |
| Docker Compose | 用配置文件管理容器服务的工具 | 管理项目专属 Neo4j 5.26.0 Community 容器与数据卷 |
| Langfuse（可选） | 模型应用的调用链观测工具 | 独立入口通过内存包装记录部分关键调用的耗时和错误，辅助定位瓶颈 |

**概念关系：** RAG 是“先检索资料，再让模型依据资料生成”的方法；Embedding 是检索前的文本向量化；LLM 是负责改写、抽取和生成的语言模型。本项目未实现模型训练或微调。原件与索引保存在本机；问题改写、关系抽取及回答所需的历史、文档块或检索片段会发送到配置的模型服务。

### 三种数据库的分工

| 存储 | 定义 | 实际保存内容 | 为什么需要 |
| --- | --- | --- | --- |
| SQLite | 以单文件保存数据、支持 SQL 与事务的关系数据库 | 文档清单、建库任务、会话、完整问答、来源 JSON、耗时 | 轻量持久化业务状态，便于恢复历史与计算指标 |
| Milvus | 面向向量相似性检索的数据库 | 文本向量、片段正文、文档 ID、页码、片段号 | 找到“表达不同、含义相近”的资料 |
| Neo4j | 以节点和关系组织数据的图数据库，使用 Cypher 查询 | 实体及关系，关系附带文档、片段、页码和逐字依据 | 通过共享实体连接不同文档，补齐两跳关系证据 |
| upload_files/ | 本地文件目录 | 按文档 ID 命名的上传原件 | 保留可下载、可核对的真实全文 |

**分工思路：** SQLite 管业务状态，Milvus 管语义检索，Neo4j 管关系查询，文件目录保留原件。备份时需要配套保留。

## 4. 架构与工作流程

### 4.1 为什么这样分层

```text
浏览器：模板、页面交互、原文阅读器、关系图谱
  ↓ HTTP / SSE
api/：参数校验、路由与响应格式
  ↓
services/：文档生命周期、任务、检索、抽取、生成
  ↓
repositories/：SQLite 数据访问
  + Milvus / Neo4j / 本地文件 / 外部模型接口
```

接口层不承担检索或 SQL 细节；服务层可以脱离 HTTP 测试；SQLite 访问集中，便于维护表结构。当前采用单体应用与函数模块，符合个人工作台的部署规模。

### 4.2 文档入库：从文件到可见资料

1. **校验与暂存：** 检查扩展名、文件名、空文件及大小，生成 UUID，保存原件。
2. **记录任务：** SQLite 写入 queued 状态，接口返回 HTTP 202，单工作线程继续处理。
3. **解析与语义分块：** 保留 PDF 页码，按相邻句向量余弦相似度合并；默认阈值 0.55，每块最多 512 字符，不跨 PDF 页合并。
4. **关系抽取：** 模型返回主体、关系、客体和逐字依据；依据必须存在于块内，主体与客体必须存在于依据中，否则任务失败。
5. **写入索引：** 串行写 Milvus 和 Neo4j；两路成功后才提交 SQLite 文档清单。
6. **完成或补偿：** 成功标记 succeeded；失败记录原因，尝试清理两种索引，清理失败时记录日志并保留文件。

任务阶段：waiting → semantic_chunking → extracting_relations → writing_vectors → writing_graph → complete。

### 4.3 一次问答：从问题到可核对回答

1. 读取近期历史，将追问改写为独立检索问题；保存时仍保留用户原问题。
2. 并行检索：Milvus 查 Top5 并过滤 L2 距离大于 1.5 的片段；Neo4j 以实体匹配为入口查询最多两跳关系。
3. 若向量有结果而图谱为空，可用向量命中文档作为图谱入口补查。
4. 按“文档 ID + 片段号”去重，以 RRF 融合排名，最多保留 12 条来源；默认混合路径按正式文档清单过滤不可见来源。
5. 用编号资料构建提示词，要求模型基于证据作答并标注 [1] 等引用；没有来源时使用固定资料不足回复。
6. SSE 发送 status → sources → graph → delta → done；出现异常发送 error。
7. 生成完整回答后保存会话、来源与耗时；中断回答保留前端提示，不作为完整回答落库。

### 4.4 数据模型与全文定位

- SQLite：documents 记录已收录文档；index_jobs 记录任务；sessions 与 messages 一对多。messages.sources 保存来源 JSON，含图谱关系信息。
- Milvus：每个片段携带 doc_id、source、chunk、page，引用由这些字段关联原文件。
- Neo4j：实体以“命名空间 + 规范化名称”唯一合并；关系用文档、片段和三元组生成稳定 ID，携带 evidence 和原文。
- 点击引用后，通过文档 ID 获取完整原件/文本，按页码与片段内容定位；文字先规范化匹配，失败后尝试较短的真实文本匹配，仍找不到则明确提示。

## 5. 关键设计点：问题、思路与取舍

| 问题 | 设计思路 | 取舍与边界 |
| --- | --- | --- |
| 固定长度切块可能拆散语义 | 主流程按相邻句语义相似度合并，并限制块长 | 增加嵌入计算；不保证所有长句语义完整。旧字符分块函数保留供兼容 |
| 单靠向量容易漏掉关系链 | 向量补语义相似，图谱通过共享实体补关系证据 | 当前是两跳查询，无复杂实体消歧，名称相同可能错误合并 |
| 两路分数不能直接相加 | RRF，即倒数排名融合，按各路名次计分 | 每路第 r 名贡献 1/(60+r)，不依赖原始分数同尺度；当前无额外重排模型 |
| 模型抽取可能凭空补充 | 抽取后校验逐字依据与主体、客体出现位置 | 能证明文本出处，不能证明关系语义一定正确 |
| 两个索引库可能只写成功一个 | 索引写完再发布清单，失败补偿，重启按原文档 ID 清理部分写入再建 | 没有跨库原子事务，也没有严格“只执行一次”保证；极端故障需排查残留 |
| 建库耗时影响页面体验 | 先持久化任务，再由单工作线程执行；状态可查询 | 这是进程内队列加持久状态，未使用 Celery/Redis；不支持多 Uvicorn 工作进程 |
| 并发写入和模型占用资源 | 写索引与删除串行；关系模型调用放在写锁外；嵌入计算另有锁 | 减少长时间持有写锁，但嵌入锁仍可能让检索等待 |
| 重复问题与首次调用较慢 | 复用模型/向量库实例，启动时按条件预热，缓存最多 128 个问题的向量召回 | 缓存的是检索结果；增删索引清缓存，未缓存最终答案 |
| 某一路服务失效 | 有可用证据时降级回答并提示；双路失败返回错误 | 无证据时仍提示资料不足，不保证故障时始终能生成答案 |
| 回答与展示难核对 | 来源编号、完整原文、局部图谱使用同一批证据；仅完整回答落库 | 图谱表示提供给模型的关系上下文，不证明每条边都被答案采用 |

基础保护已包含：UUID 原件命名、输入校验、SQL/Cypher 参数化、Markdown HTML 清洗、来源文字安全展示、本机 Host/Origin 限制。当前定位是本地个人应用，尚无账号体系或多租户权限隔离。

## 6. 高频追问：简短回答

**为什么不用一个数据库？**

业务记录、向量相似性和图遍历是不同访问需求。分开后职责清楚，代价是跨存储一致性更复杂，所以加入清单发布、补偿和恢复。

**多轮对话是直接把历史都交给回答模型吗？**

先用最近历史改写问题，正式回答只使用本次检索证据。这样限制上下文长度，也降低旧答案直接污染新答案的风险；改写本身仍可能出错。

**如何降低幻觉？**

无证据时固定回复资料不足；有证据时约束生成、输出引用并提供原文核对；图谱入库前校验逐字依据。没有实现对每句回答的自动事实证明。

**SSE 为什么适合？**

页面主要接收模型逐段输出，HTTP 流即可满足单向推送需求。本项目使用 POST + fetch 读取流，后端用 StreamingResponse 编码事件。

**IVF_FLAT、L2、WAL 分别是什么？**

IVF_FLAT 将向量按聚类分桶，在选中的桶内比较；这里配置 nlist=100、nprobe=10。L2 是欧氏距离度量，这里距离越小越相近。WAL 是 SQLite 预写日志模式，有助于读写并存，但不代表支持无限并发写入。

**怎么判断项目有效？**

分开看答案是否正确、必要引用文件是否覆盖、首字耗时和完整耗时。页面“资料命中率”只表示有来源的问答占完成问答的比例，不是准确率。

**下一步优先做什么？**

先补真实语料评测、实体消歧和失败任务重试；若需要多人使用，再引入权限、独立任务队列和跨存储对账。按场景扩展，不把计划描述为现有功能。

## 7. 现场演示：约 6 分钟

### 7.1 演示前准备

- 启动 Docker Desktop，确认已有 Milvus 可用；检查本机 .env 的模型、嵌入模型和 Neo4j 配置。
- 双击 [启动项目.cmd](../启动_停止项目/启动项目.cmd)，默认访问 http://127.0.0.1:8010。
- 检查 /health 与 /api/status：网页正常、database=true、模型已配置、图谱已启用并 connected=true。/health 只证明网页存活；模型配置存在也不证明外部接口可调用，提前完成一次真实问答。
- 如已有资料，等待嵌入预热完成；首次建库可能需要加载模型。准备一份可提取文字的 PDF，用于原文阅读演示。
- 提前准备下面两份 UTF-8 文本；使用新上传且已完成建库的资料，避免旧文档无图谱。优先使用演示专用数据空间。

| 文件 | 内容 |
| --- | --- |
| 面试演示-负责人.txt | 林然负责天枢项目。 |
| 面试演示-技术.txt | 天枢项目使用青岚数据库。 |

“青岚数据库”只是演示资料里的名称，不是项目实际使用的数据库。

### 7.2 演示步骤与讲解

| 时间 | 操作 | 讲解重点与通过标准 |
| --- | --- | --- |
| 0:00—0:30 | 打开工作台和知识库 | 一句话讲目标，说明当前资料、片段和服务状态 |
| 0:30—1:30 | 上传两份文本，展示任务阶段并等待完成 | 202 只代表接收任务；成功后应新增两份文档，才算完成入库 |
| 1:30—2:30 | 新建会话，问“林然负责的项目使用什么数据库？请说明关系链。” | 回答应串联“林然→天枢→青岚”，来源覆盖两文档；图谱应包含对应三实体、两关系 |
| 2:30—3:30 | 点击两处引用和图谱中间节点 | 打开对应完整原文并定位，证明回答能回到证据；可再展示提前准备的 PDF |
| 3:30—4:00 | 同一会话追问“它由谁负责？” | 应结合前文识别项目，回答林然；解释独立问题改写 |
| 4:00—4:30 | 刷新页面，打开原会话 | 回答、来源和图谱恢复，证明持久化可用 |
| 4:30—5:00 | 问“玄鸟项目的负责人是谁？” | 在演示资料未提供该事实的前提下，应说明资料不足，不编造人名 |
| 5:00—5:30 | 打开数据洞察 | 展示新增记录、来源和耗时，解释命中率不等于正确率 |
| 5:30—6:00 | 仅删除两份本次演示文档，再开新会话核查 | 文档清单移除；后续检索不应再返回这两份文档。历史保留，但原文入口提示已移除 |

若图谱或答案不符合预期，现场沿“任务是否成功 → 改写问题 → 实际 sources → 原文依据”排查；不要用预期结果替代真实返回。

### 7.3 临场故障处理

- **网页打开，问答失败：** 查看 /api/status 和 temp/runtime/server-error.log，区分向量服务、图谱、模型配置及外部模型调用失败。
- **建库失败：** 先读任务原因，确认文档含文字、模型服务和双库连接可用；失败任务没有自动重试入口，可修复后重新上传。
- **外部模型临时不可用：** 展示已保存的历史、原文和下节评测记录，并说明实时调用未成功。
- **结束：** 双击 [停止项目.cmd](../启动_停止项目/停止项目.cmd) 停止网页；数据库仍运行。观测入口与普通入口共用 8010 端口，应择一启动。

## 9. 闭环复核与代码索引

面试前按顺序复核，任一步失败都先定位原因，再重新走该步骤：

- [ ] **技术对得上：** 技术栈有依赖或源码依据，默认配置与实际部署区分清楚，个人贡献符合事实。
- [ ] **上传有结果：** 文件接收 → 任务 succeeded → 文档出现在清单，不能将 202 当作完成。
- [ ] **回答有证据：** 两文档问题 → 答案关系链 → 两份来源 → 完整原文定位。
- [ ] **上下文可恢复：** 同会话追问正确，刷新后历史、来源和图谱仍可查看。
- [ ] **边界有反馈：** 无依据不编造，任务失败有原因，未完成回答不冒充完成记录。
- [ ] **指标口径一致：** 命中率与正确率分开，首字与完整耗时分开，小样本与普遍效果分开。
- [ ] **清理不残留：** 删除演示文档后，新检索不再返回其来源；历史与原件删除后的表现符合说明。
